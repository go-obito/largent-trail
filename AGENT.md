# AGENT.md — Largent

Largent is a mobile-first personal finance PWA with a Python/FastAPI backend (frontend to follow). This file tells AI coding agents how to set up, build, test, and contribute to the repo.

**Use this file when:** writing or changing code, migrations, tests, or docs in this repository.

**Always:** follow the conventions below, run `make check` before finishing, and ask when a task conflicts with this file or the spec is unclear.

---

## 1. Product in one paragraph

Largent is a mobile-first personal finance app (PWA) for everyday money management. Users record income and spending, set weekly or monthly category budgets, and see a simple **daily spending target** that adapts to what they have already spent that week. They can plan purchases in a prioritized wishlist, view reports, and import bank or mobile-money statements from CSV. It must work offline and sync when connectivity returns. Launch market: **Ghana, single currency (GHS, Ghanaian cedi, symbol ₵)**.

This is a **from-scratch rebuild** of a single-user prototype. The prototype is a feature reference only. Do not copy its technology, structure, or code.

## 2. Scope and status

**In scope now (backend MVP):** auth integration, users, accounts, categories, transactions, budgets, wishlist/needs, dashboard and report aggregates, CSV import, offline sync API, data export, account deletion.

**Deferred. Do not build or scaffold unless explicitly asked:**
- Bank or mobile-money API sync
- Multi-currency and FX (but store the currency code, see §5)
- Shared or household workspaces (rows are owned by a single `user_id`)
- Habit tracking beyond budget adherence. The product spec for habits is **not yet decided**. Never invent habit features.
- Frontend (it gets its own section and prompts later)

## 5. Money rules (critical)

1. **Never use floats for money.** Store and transmit amounts as **integer minor units** (pesewas: ₵1.00 = 100). Column name: `amount_minor BIGINT`. API field: `amount_minor` (integer).
2. Every money row has `currency CHAR(3)`; for now the only allowed value is `GHS`. Validate it, do not hard-code it away.
3. `amount_minor` is always **positive**. Direction comes from `kind` (`income` | `expense`). No negative amounts.
4. Convert to a display `Decimal` only at the presentation edge. Implement formatting in `domain/money.py`.
5. Balance is **derived** (sum of income minus expenses plus the account's opening balance), never stored as a mutable number.

## 6. Core domain rules

**Periods.** A user has an IANA timezone (default `Africa/Accra`). Weeks start **Monday**. All period boundaries are computed in the user's timezone, then converted to UTC for queries. `occurred_on` is a `DATE` in the user's local time plus a `created_at` timestamp.

**Daily spending target** (pure function in `domain/daily_target.py`):

```
weekly_budget_total = sum of weekly budget limits for expense categories
                      (monthly budgets are prorated: limit × 7 / days_in_month)
spent_before_today  = expenses this week excluding today
days_left           = days remaining in the week including today (1..7)
daily_target        = max(0, (weekly_budget_total − spent_before_today) / days_left)
left_today          = daily_target − spent_today
status              = "within_target" | "near_limit" (>= 80% used) | "over_target"
```

Reference test cases (must exist as unit tests): weekly budgets ₵78.00 + ₵200.00 = ₵278.00, Monday, nothing spent earlier → target ₵39.71 (rounded down to the pesewa), spent today ₵13.00 → left ₵26.71. Add cases for midweek, overspent week, no budgets (target is null, not zero), Sunday, and timezone-boundary transactions.

**Budgets.** Per expense category, `period` is `weekly` or `monthly`, `limit_minor` > 0, one active budget per (user, category, period). Progress and near/over-limit status are computed, not stored.

**Priority Needs.** Per user, an ordered list of things to buy: name, `target_minor`, `priority` (`high | medium | low`), `position`, optional note and source URL. Display order is `position`; new items and priority changes are auto-placed after the last item of equal or higher priority, and a manual reorder may override that. Savings are tracked with an **append-only allocation ledger** (`allocate` / `release`, positive amounts). `allocated_minor` per need is derived from the ledger. `savings_pool = total balance of non-archived accounts`; `unallocated = savings_pool − sum(allocated of active needs)`. Allocating moves money inside the pool and never changes total savings (no double counting). Allocation cannot exceed `unallocated` or the need's remaining amount. A need is complete when `allocated_minor >= target_minor`; completed needs stay visible with progress capped at 100% until deleted. Deleting a need with allocated savings requires reconciliation: `release` (back to unallocated) or `purchased` (release plus an expense transaction for that amount).

## 7. Multi-tenancy and data privacy

- Every tenant table has `user_id UUID NOT NULL` with an index, and **Postgres Row-Level Security** enabled and forced.
- The application connects as a **non-superuser role without `BYPASSRLS`**. Each request sets `SET LOCAL app.user_id = '<uuid>'` inside its transaction; policies compare `user_id = current_setting('app.user_id')::uuid`.
- **Explicit exception: the `users` table.** It has no `user_id` column. It is isolated by its own primary key: RLS is enabled and forced, and the `user_self` policy allows `SELECT` and `UPDATE` only where `id = current_setting('app.user_id')`. The app role has no `INSERT` or `DELETE` privilege on it. Users are created and resolved only through the narrow `SECURITY DEFINER` functions `provision_user` and `resolve_user` (B2). These run as `largent_migrator`, which is subject to `FORCE` RLS, so `users` also carries policies `TO largent_migrator` only, granting `SELECT` and `INSERT` (never `UPDATE` or `DELETE`). The app role never matches them, and hard deletion will go through a similar dedicated function (B10). The tenant-table guardrail test keeps an explicit exception list, and `users` is the only entry. Adding to that list requires an ADR.
- **Composite foreign keys.** Foreign key checks bypass RLS, so a plain FK could let one tenant reference another tenant's row. Every tenant table therefore has `UNIQUE (user_id, id)`, and every child table references its parent with a composite FK `(user_id, parent_id) → parent (user_id, id)`. Cross-tenant references are then impossible at the database level.
- Services still filter by `user_id` explicitly (defense in depth). RLS is the safety net, not the only check.
- Never accept `user_id` from request bodies or query strings. It comes only from the verified auth token.
- **Required test:** user A cannot read, update, or delete user B's data through any endpoint, and a raw query without `app.user_id` set returns nothing. This test must stay green forever.
- Never log request bodies, tokens, descriptions, notes, or amounts. Log IDs and status only.
- Provide `GET /v1/me/export` (full JSON export) and `DELETE /v1/me` (hard-delete everything for the user, including derived and queued data).

## 8. Authentication

- Identity is delegated to an external provider (currently **Clerk**: email one-time code and Google sign-in). The backend only **verifies JWTs** (JWKS fetched and cached, validate `iss`, `aud`/`azp`, `exp`, `nbf`) and never handles passwords.
- Put this behind an `AuthProvider` protocol in `core/security.py` so the provider can be swapped (record the decision in `docs/adr/0001-auth-provider.md`).
- First sight of a valid token's `sub` creates the local `users` row (just-in-time provisioning). The local `users.id` is the identifier used everywhere else.
- All `/v1/*` routes require auth except `/healthz` and `/readyz`.

## 9. API conventions

- Versioned under `/v1`. JSON only. Snake_case fields. Timestamps in UTC ISO-8601; dates as `YYYY-MM-DD`.
- Errors use **RFC 9457 problem+json** with a stable `code` field. Never leak stack traces.
- List endpoints use **cursor pagination** (`limit`, `cursor`), never offset.
- Idempotent writes. Creating a synced entity is idempotent by its **client-generated UUIDv7 `id`**: replaying the same `id` with an identical payload returns the original row with 200; the same `id` with a different payload returns 409 `id_conflict`. Sync push (§10) is idempotent by `client_mutation_id`. Any other retryable, non-idempotent write (for example a CSV import commit) accepts an `Idempotency-Key` header; replaying the same key returns the original result.
- Rate limits per user and per IP (Redis). Stricter on import and auth-adjacent endpoints.
- Export the OpenAPI schema to `apps/api/openapi.json` on every API change (`make openapi`); the frontend client is generated from it. CI fails if the file is stale.
- CORS uses an explicit allowlist from config, never `*`.

## 10. Offline sync contract

Clients are local-first and sync through two endpoints:

- `POST /v1/sync/push`: a batch of mutations `{client_mutation_id, entity, op: upsert|delete, id, data, base_version?}`. Each is applied idempotently and the response reports per-mutation status.
- `GET /v1/sync/pull?cursor=…`: returns all changes (including tombstones) since the cursor, ordered by a per-user monotonic `server_seq`, plus the next cursor.

Rules:
- Synced tables carry: `id` (client UUIDv7), `created_at`, `updated_at`, `deleted_at` (soft delete), and `server_seq`. **Sequencing rule:** tables created before B8 (accounts, categories, transactions, budgets, wishlist) are created without `server_seq`. The B8 migration adds the column, the per-user counter and a backfill to all of them. Every synced table created from B8 onward includes `server_seq` from the start. This is the designed order, not an exception to be re-litigated per step.
- Conflict policy: **last-write-wins per field** by `updated_at` for most entities. Wishlist ordering and budgets get explicit merge rules documented in an ADR.
- A `mutations` table keyed by `(user_id, client_mutation_id)` guarantees replays are no-ops.
- Soft-deleted rows are purged only by a retention job after the retention window, never by normal requests.

## 11. CSV import

Two-step flow (preview, then commit), processed synchronously inside the request because files are capped at 1,000 rows (the worker is reserved for later heavy jobs):
1. **Preview**: upload CSV, detect delimiter and encoding, return headers and sample rows.
2. **Commit**: client sends column mapping (date, description, amount, optional debit/credit columns) plus per-row category choices; server validates and inserts.

Constraints carried over from the prototype: **max 2 MB, max 1,000 rows**. Reject larger files with a clear error. Dedupe on `sha256(user_id | date | amount_minor | normalized_description | account_id)`; skip duplicates and report counts. Every import creates an `import_batch` so it can be undone as a unit. Treat uploads as hostile: no formula execution, strict parsing, strip control characters, bound memory use. Parse amounts with `Decimal`, then convert to minor units.

## 12. Security checklist (applies to every change)

- Validate all input with Pydantic; set max lengths on every string field.
- Parameterized queries only. No string-built SQL.
- Secrets only via environment variables; never committed, never logged. Provide `.env.example`.
- Security headers, HTTPS-only cookies if any are used, strict CORS.
- Run `pip-audit` (or `uv` audit) and a secret scanner in CI.
- Principle of least privilege for the DB role and any cloud credentials.
- Database backups with a **tested** restore procedure (documented in `docs/runbooks/`).

## 13. Testing and quality gates

**Fast mode (current policy for feature development, B5 onward):** do **not** write new tests unless a prompt explicitly asks for one. The existing suite and the RLS guardrail test must stay green, and `make check` runs once per checkpoint. Everything below describes the full policy that applies again before public launch, when a test backfill happens as part of B10 hardening (tenant isolation for every module, domain-logic unit tests, sync and import edge cases). Do not delete or weaken existing tests to make a build pass.


`make check` must pass before any commit: `ruff format --check`, `ruff check`, `mypy --strict`, unit and integration tests.

- Domain logic (`domain/`) needs ≥ 95% coverage and tests written first for money and daily-target rules.
- Integration tests use a real Postgres container. Do not mock the database.
- Every endpoint has at least: happy path, validation failure, unauthenticated, and wrong-tenant tests.
- Migrations: forward-only in production. **Never edit a migration that has been committed**; add a new one. Test `upgrade head` from empty and `downgrade` one step in CI.

## 15. How to work (agent workflow)

1. **Plan before coding** for any task touching more than one file: state the plan in a few lines, then proceed.
2. Work in **small, reviewable increments**: one module or concern per commit. Conventional Commits (`feat:`, `fix:`, `test:`, `docs:`, `chore:`).
3. Write or update tests in the same change as the code.
4. If the spec is ambiguous or a decision is missing, **ask**; do not guess on money, auth, tenancy, or sync behavior.
5. Record non-obvious decisions as short ADRs in `docs/adr/`.
6. Do not add features, endpoints, or tables that were not requested. No placeholder TODOs; open a note in `docs/` instead.
7. Keep functions small and typed. No `Any` without a comment explaining why.
8. Update this file's Status section and the relevant docs when behavior changes.
9. At the end of each task, report: what changed, how to run it, what was tested, and anything left undecided.

## 16. Definition of done

A task is done only when: code is merged-ready, `make check` passes, new behavior is tested (including the wrong-tenant case), OpenAPI is regenerated, migrations are included and reviewed, docs and ADRs are updated, and no secrets or personal data are in logs or fixtures.
